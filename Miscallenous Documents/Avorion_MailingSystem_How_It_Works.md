# Avorion Mission & Mail System Analysis

This document explores the structure and mechanics of vanilla Avorion missions, story missions, and the player mailing system, as well as an analysis of community-created missions.

## Vanilla Mission Structures

Vanilla Avorion features two distinct paradigms for writing missions, based on which library they include.

### 1. Basic Missions (`include("mission")`)

Scripts like `delivery.lua` use the basic mission library.

- They rely on a global `missionData` table to store state (e.g., `missionData.timeLeft`, `missionData.good`).
- Logic is handled via top-level event functions (like `onStartDialog()`, `onDeliver()`).
- State management and advancing the mission require manual handling.
- Any function the client needs to call on the server (`onDeliver()` here) must still be registered with `callable(nil, "onDeliver")`, exactly like a plain non-namespaced script. `delivery.lua` includes `"callable"` and calls this at the bottom of the file. Miss it and the client-side `invokeServerFunction()` call silently fails to reach the server.

### 2. Structured Missions (`include("structuredmission")`)

Most story missions (like `swoksmission.lua`) use the structured mission system.

- They use a state machine defined by `mission.phases`.
- Each phase can have its own event hooks (`onBeginServer`, `onSectorEntered`, `playerCallbacks`).
- Advancing the mission is as simple as calling `setPhase(2)` or `nextPhase()`.
- `setPhase()` automatically pushes `mission.data` (including `mission.data.description`) to the client via `sync()`. The description text itself is not generated by the framework, though; each phase's `onBeginServer` (or similar) still has to set `mission.data.description` by hand, as the story missions in this project do.

## Vanilla Mail System

The mailing system in Avorion allows scripts to send messages directly to players. It's often used as an immersive way to start or progress missions.

### Creating and Sending Mail

Mail is constructed using the `Mail()` object and then sent to a player using `player:addMail(mail)`.

```lua
local mail = Mail()
mail.text = "Hello!\\n\\nWe need your help..."%_T
mail.header = "Urgent Request /* Mail Subject */"%_T
mail.sender = "A Friend"%_T
mail.id = "Unique_Mail_Identifier" -- Used to track if the player reads it

local player = Player()
player:addMail(mail)
```

`mail.text`, `mail.header`, and `mail.sender` are typed as `Format`, not a plain string, and every vanilla mail (e.g. `aimission.lua`) wraps them with `%_T` for localization. The `/* Mail Subject */`-style trailing comment inside the header string is a real vanilla convention too, not a formatting mistake; it disambiguates otherwise-identical header text for the translation pipeline.

### Reacting to Mail

Scripts can react when a player reads a specific mail by hooking into the `onMailRead` event. In structured missions, this is often handled inside a phase's `playerCallbacks`.

```lua
mission.phases[1].playerCallbacks =
{
    {
        name = "onMailRead",
        func = function(playerIndex, mailIndex, mailId)
            if mailId == "Story_Swoks_Mission" then
                setPhase(2) -- Move to the next phase when mail is read
            end
        end
    }
}
```

## Community Modding Patterns (Knifeheart)

Looking at community mods, specifically Knifeheart's custom missions (`New Mission - Ambush Pirate Raiders` and `New Campaign - Vengeance Be My Name`), we see an advanced and highly structured approach:

### 1. Exclusive Use of `structuredmission`

Community modders heavily favor the `structuredmission` API over the basic mission API because of its robustness. It provides built-in phase states, timers, and triggers without needing to write custom `update` loop logic.

### 2. Custom Initialization Overrides

Modders often override the base `initialize` function to inject custom `_Data_in` parameters before calling the original init function:

```lua
local CustomMission_init = initialize
function initialize(_Data_in)
    if onServer() and not _restoring then
        mission.data.custom.dangerLevel = _Data_in.dangerLevel
        CustomMission_init(_Data_in)
    else
        CustomMission_init()
    end
end
```

### 3. Phase Timers and Triggers

Instead of manually tracking time, structured missions support built-in phase timers and triggers:

```lua
mission.phases[1].timers = {
    {
        time = 10, 
        callback = function() 
            if conditionMet() then nextPhase() end
        end,
        repeating = true
    }
}

mission.phases[1].triggers = {
    {
        condition = function() return atTargetLocation() end,
        callback = function() spawnEnemies() end,
        repeating = false
    }
}
```

### 4. Advanced Data Structures inside `mission.data.custom`

In complex story missions like "Pirate Recon" (Vengeance Be My Name), `mission.data.custom` is heavily utilized to store complex tables, such as transmission arrays with dynamic localized string formatting:

```lua
mission.data.custom.transmissionTable = {
    { 
        text = "That damn security team shot ${_NAME}.", 
        time = 78, 
        sent = false, 
        format = true, 
        formatFunc = function()
            local lang = Language(Seed(random():getFloat(0.0, 1000000.0)))
            return { _NAME = lang:getName() }
        end 
    }
}
```
